AI Coding Tool Comparison System

Python core — deterministic, offline Agent harness — Claude Code (.claude/) One JSON envelope per command
01 · Overview

What is tool-eval?

A CLI that automates the research, profiling, and comparison of AI coding tools, driven end to end from a Claude Code session.

What it does

  • Research — gathers facts about a tool from official sources
  • Profile — stores a structured, validated profile per tool
  • Compare — builds one self-contained HTML report across tools

Core design principle

Strict separation of responsibilities:

  • The Python core is deterministic and offline — it validates, merges, and publishes, but never calls a model or the network
  • All LLM reasoning (research, curation judgement, web access) is delegated to an external agent harness under .claude/
No API key or model SDK is required by the Python core — all LLM work runs inside the Claude Code harness; Python only enforces structure and consistency of the data.

04 · CLI surface

The CLI is the determinism boundary

Every command below is plain, testable Python — no model calls. This is the mechanism the harness relies on for reproducibility.

config

  • config validate

run

  • run init research
  • run status <run_id>
  • run resume-check <run_id>
  • run fail <run_id> "<reason>"

research

  • research create-feature-tasks <run_id> [--isolate <feature_id>]
  • research merge <run_id>
  • research curate-candidates <run_id> <decisions.json>
  • research prepare-repair <run_id> [--feature-id <feature_id>]

profile

  • profile validate <profile.json> [--check-completeness]
  • profile publish <run_id> <tool_id> [--check-completeness]
  • profile list

compare

  • compare build --tools <id> <id> [...] [--out <file.html>]

work

  • work recover
  • work cleanup
Every command prints exactly one JSON envelope to stdout: {status, code, run_id, next_action, artifacts, errors}. No free-form output, no hidden side effects — the harness reads next_action to decide what to do next.

Accepting a new feature candidate at the curation gate bumps the feature-taxonomy revision and marks every other tool's published profile requires_research — only the newly accepted feature is missing, not the whole profile. research create-feature-tasks <run_id> --isolate <feature_id> re-researches just that one feature per tool, instead of a full re-run.
compare build (step 9) is invoked separately over tools that already have a published profile — it never triggers research itself; it only computes freshness/diff flags and renders the HTML report.
06 · Collaboration

Harness, agents, and skills

The operator never calls the CLI directly — three entry skills hand off to a shared orchestration workflow.

Entry skills

  • /tool-eval-research <tool>
  • /tool-eval-compare <id...>
  • /tool-eval-resume <run_id>

Validate arguments, then hand off to the tool-eval-orchestration skill.

Orchestrator Agent

Started as claude --agent tool-eval-orchestrator. Owns the run end to end: calls the CLI, delegates tasks to workers, enforces the single curation gate and the bounded repair loop, triggers publication.

Worker Agents

Isolated, one delegation layer deep. Each executes a single research task from official sources and returns the result as data. No access to bash/config/publication, cannot delegate further.

Worker isolation is a deliberate boundary: research from untrusted external sources can never touch config, schemas, or published profiles directly — it only returns as data to the Python layer.
07 · Known limitations

Known limitations: WebSearch / WebFetch

Constraints observed in the current environment that limit full autonomy.

WebSearch requires approval

Org policy requires manual approval on every WebSearch call. Each research task's search request pauses and waits for operator confirmation — the run cannot proceed unattended.

Per-session search limit

There is a cap on WebSearch calls per session. This further limits how much research a single run can complete before hitting the ceiling.

WebFetch is blocked

WebFetch is currently disabled entirely. Enabling it could reduce reliance on repeated WebSearch calls (e.g. crawling within an already-approved domain) — that workaround is not available yet.

Net effect: fully autonomous, unattended research runs are not currently possible — sessions need an operator present to approve search calls until a workaround is found.
